# 지정 계정 운영 심사 검증 — 결과·설계 대조

2026-11-08. [설계](../02-design/features/live-editorial-validation.design.md).

## 실제 운영 절차

지정 심사위원장 계정은 저자와 위원장 화면을 겸하고, 기존 테스트위원 1·2는 reviewer/AE 겸임으로 로그인했다.
비밀번호·회원 프로필·명부·운영 단계·메일 설정은 바꾸지 않았다. [E2E TEST] 합성 원고 1건만 사용했다.

| 단계 | 실제 확인 |
| --- | --- |
| 신규 투고 | 저자 화면의 초안/PDF 저장·제출 완료, 제출본 v1·접수 시각 생성 |
| 위원장 배정 | 지정 2계정 배정, 현재 제출본 심사 2명 |
| 1차 심사 | 두 계정이 이해관계 확인·권고·의견 제출 |
| AE 수정 요청 | 담당 AE가 확인 dialog로 공개, 저자에게 익명 의견 2건·수정 요청 표시 |
| 재제출 | 같은 원고에 PDF v2, 제출 시각 변경·이전 의견 보존·현재 배정 0으로 초기화 |
| 재심·최종 판정 | 위원장 새 2인 배정, 재심 2건, 담당 AE 최종 채택 |
| 결과·이력 | 저자 현재 의견 2건, 위원장 이전 의견 2건 + 현재 2건, PDF 버전 2개 |

일반 workflow `is_test=false`로 생성된 20건 모두 DB sent이며, Resend Emails 두 페이지에서 각각의 provider ID를
대조해 **20/20 Delivered**를 확인했다. 저자/위원장 계정 10건, AE1/심사위원 계정 8건, 심사위원2 계정 2건이다.
신규·재제출 알림 각 2건, 저자 접수 확인 각 1건, 배정 4건, 심사의견 알림 8건, 판정 2건이다.
발송 기록은 수신 메일 열람을 의미하지 않는다. 지정 수신자 외 발송이나 테스트용 bypass는 없었다.

## 발견·수정 및 격리 회귀

배정 reviewer와 AE를 겸하면 타 분야에 배정된 원고가 AE 목록에 섞이는 문제를 운영에서 재현했다.
기존 papers RLS가 author/reviewer/editor 조회를 함께 허용하므로 UI의 편집 목록·통계·상세 범위를
활성 담당 분야와 이해관계 조건으로 좁혔다. 위원장 전체 목록과 개인 reviewer 접근, DB 권한은 보존한다.

새 격리 Supabase에서 브라우저 **9묶음** PASS: 타 분야 겸임 배정, 본인 소유, 공동저자 제외, reviewer 접근,
권한 없는 판정/미완료·오래된 판정 차단, 두 분야 수정/재심/채택/반려 및 검색/키보드/모바일을 확인했다.
기존 v1~v4 메일 경계 **8묶음** PASS(30개 workflow, provider 접수 36개·요청 41개, 응답 유실 복구 포함).
TypeScript/build, JS syntax, Python AST, diff PASS. DB migration/API/메일 양식은 변경하지 않는다.

운영 증거는 `/tmp/co-rnbd-live-20261108/`, 격리 결과는 `/tmp/co-rnbd-live-regression-20261108/`에
비공개로 보관한다. 키/토큰/세션은 출력·커밋하지 않는다. 실제 비위원장 저자 RLS 차단은 격리 계정으로 검증했다.
배포 후 같은 원고에서 AE 범위·정상 인증 판정 거절·두 심사위원의 PDF 원본 일치·저자 최종 결과를 재확인하고
테스트 세션만 만료한다. 최종 배포·운영 재확인 결과는 PR 설명에 기록한다. 원고·심사·메일 이력은 삭제하지 않는다.
