# DB 연결과 포털 응답 최적화 설계

## 공통 연결 설정

`conference-client.js`의 세션 캐시는 저장된 `data.url`, `data.publishableKey`, 유효한 `cachedAt`을 검사한다. 5분 TTL을 지키며 만료·손상·저장소 차단 시 API로 복구한다. 동시에 요청한 호출은 진행 중인 Promise를 공유한다. 완료된 Promise는 해제하여 같은 페이지에서도 TTL 이후 재조회할 수 있다. 캐시에는 공개 설정만 저장하며 역할, 단계, 개인 데이터는 저장하지 않는다.

## 위원장 목록과 상세

- 목록은 검색·통계·심사 진행·최종본 확인에 필요한 열만 명시한다. 원고 초록, 연락 이메일, 심사 전문, 파일 경로, 처리 이력은 포함하지 않는다.
- 300행씩 조회하는 기존 페이지 처리를 유지한다. 회원 조회는 배정 후보 및 심사자 이름 표시를 위해 유지한다.
- 상세를 열거나 새로고침할 때 해당 원고의 전체 관계 데이터와 처리 이력을 병렬 조회한다. 회차·접수 상태 필터를 상세에도 적용한다.
- 목록 요약과 선택된 전체 원고는 별도 상태로 관리한다. 판정에는 반드시 최신 상세의 전체 심사 행을 전송한다.
- 상세 조회 중에는 이전 상세를 숨기고 진행 메시지를 표시한다. 실패하면 목록으로 돌아가 재시도할 수 있게 한다. 뒤로가기나 다른 조회로 무효화된 응답은 렌더링하지 않는다.
- 상세 조회 후 해당 목록 요약을 갱신해 뒤로가기로 돌아왔을 때 최신 상태를 표시한다.

## 참가신청

초기 명시적 load가 있으므로 INITIAL_SESSION을 다시 처리하지 않는다. TOKEN_REFRESHED 및 동일 계정 SIGNED_IN은 작성 중인 폼을 초기화하지 않는다. 실제 계정 변경·로그아웃·USER_UPDATED 시 재조회하며 기존 generation 검사를 유지한다.

## 검증

투고 화면은 회차와 인증 초기화가 끝난 후 한 번만 작업 공간을 조회한다. 진행 중인 조회를 공유하고 실제 계정 변경 시 generation으로 기존 응답을 무효화한다. TOKEN_REFRESHED나 동일 계정 SIGNED_IN은 원고·프로필 폼을 다시 렌더링하지 않는다. 저자·심사 목록도 계정 및 generation을 확인한 뒤 반영한다.

- 로컬 실제 Auth/PostgREST 연결에서 화면 준비 시점, API별 횟수, 디코딩 응답 바이트를 기록한다. 개발 서버의 시간은 운영 성능으로 해석하지 않는다.
- 캐시 유효/만료/손상/차단/실패 후 재시도 및 중복 호출을 확인한다.
- 상세 실패 복구, 목록에 민감한 본문이 없는지, 최신 상세 스냅샷, 모바일 overflow, 참가 폼 보존 및 로그아웃을 확인한다.
- 기존 chair desk 및 동시성 검증을 모두 실행한다. 타입 검사·프로덕션 빌드·JS 문법·diff 검사를 수행한다.
- 운영에서는 공개 설정·공개 데이터·익명 원고/프로필/판정 접근 거부와 배포 SHA를 확인한다.
