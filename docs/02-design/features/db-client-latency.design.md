# DB 연결·화면 응답 최적화 설계

## 확인한 기준 상태

운영 `/api/config`, Supabase 공개 회차·설정, Auth 설정이 정상 응답한다. 익명 프로필·원고·심사·참가 신청 조회는 401로 거부된다. 공개 요청 3회 측정에서 사이트 HTML과 설정·회차 조회는 대체로 수십 ms이며, Auth 설정은 첫 요청이 더 느릴 수 있다. 따라서 현재 자료량에서 인덱스나 DB 설정 변경의 근거는 부족하다.

## 클라이언트 변경

1. 참가 신청 화면: 서로 의존하지 않는 `conference_settings`와 현재 사용자 확인을 함께 시작한다. 사용자 확인 후 프로필과 본인 참가 신청을 함께 조회한다. 인증 세대 번호와 사용자 ID 검사로 로그아웃 중 도착한 응답은 무시한다.
2. 투고 화면: 프로필과 역할을 함께 조회한다. 저자가 원고를 열 때 저자 목록과 파일 목록을, 심사위원이 열 때 저자 목록과 파일 목록을, 위원장이 열 때 저자·심사·파일 목록을 함께 조회한다. 각 요청의 기존 RLS와 오류 처리 방식을 유지한다.
3. 초기 세션 이벤트는 명시적인 초기 로드가 담당한다. 이벤트 구독은 이후 로그인·로그아웃·사용자 정보 변경에 반응한다.

독립 조회만 병렬화하며, 회차를 알아야 하는 조회와 인증이 필요한 조회의 순서는 유지한다. 요청 수와 조회 필드, 공개 권한은 늘리지 않는다.

## 검증

- 공개 API 응답과 비공개 테이블의 익명 차단을 다시 확인한다.
- 변경한 JavaScript의 구문 검사와 Next.js 타입 검사·빌드를 실행한다.
- 프리뷰에서 비로그인 투고·참가 화면의 정상 표시와 오류가 없는지 확인한다.
- 인증된 저자·심사위원·위원장 동작과 실제 지연 개선 수치는 계정별 검증 전까지 미확인으로 남긴다.
