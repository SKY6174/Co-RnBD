# 로그인 이후 저장 흐름 검증 계획

2026-11-07 · 기준 e74d8dc · 운영 데이터와 분리한 일회성 로컬 Supabase 사용.

- 현재 마이그레이션 전체를 빈 테스트 DB에 적용한다. 운영 DB 복제·운영 자격 증명은 사용하지 않는다.
- 실제 Auth 계정과 저자·심사위원 2명·위원장·비배정 회원을 생성한다.
- 브라우저에서 프로필, 초안/PDF, 투고, 심사 배정·저장·제출, 수정 요청·재투고,
  채택·최종 PDF와 위원장 확인까지 검증한다.
- 참가 신청·수정·중복 방지, 위원장 확정·체크인, 발급기관·납부 저장,
  참가확인증·영수증·거래명세서 발급·열람·인쇄·취소·재발급을 검증한다.
- DB 행·파일 해시·새로고침 이후 화면과 접근 거부를 근거로 기록한다.
- 문제는 최소 수정과 회귀 검사로 해결한다. 원격 적용이 필요한 경우 영향·복구를 검토한다.
- PR·CI·머지·운영 배포 후 읽기 전용 운영 검증으로 마무리한다.

기존 설계: paper-submission-system, conference-operations, member-documents.
로컬 합성 계정·파일만 사용하며 메일은 로컬 메일함에서만 처리한다.
운영 OAuth 계정과 결제/이메일 외부 전송은 시험하지 않는다.
