# DB 연결과 포털 응답 최적화 (2026-10-15)

## 목표와 범위

실제 배포 설정·Supabase 스키마·RLS·인덱스를 확인하고, 브라우저에서 확인된 불필요한 요청과 응답 크기를 줄인다. 기존 투고·심사 설계와 판정 동시성 검증을 유지한다.

## 확인한 문제

- 공통 연결 설정은 `{ cachedAt, data }`로 저장하지만 읽을 때 최상위 URL/key를 검사하여 매번 캐시가 무효화된다.
- 위원장 목록이 모든 원고의 초록·심사 전문·파일 경로를 함께 조회한다.
- 참가신청 시작 후 `INITIAL_SESSION` 이벤트가 동일한 회원·설정·신청 조회를 반복한다.
- 실제 측정에서 투고 화면의 인증 초기화와 명시적 시작 조회가 겹쳐 회원·원고·심사를 3회 조회한다.

## 완료 기준

1. 운영 연결·공개 조회·익명 거부·마이그레이션 상태를 확인한다.
2. 동일한 로컬 fixture와 브라우저로 수정 전후 요청 수와 응답 바이트를 비교한다.
3. 원고 상세는 열 때 최신 DB 내용을 조회하며 판정용 전체 심사 스냅샷을 유지한다.
4. 투고·배정·심사·판정·최종본·권한·동시성 회귀 검증을 통과한다.
5. PR, Preview 확인, 병합, 운영 배포 및 읽기 전용 검증을 완료한다.

## 데이터와 배포 영향

운영 데이터 변경이나 신규 DB 마이그레이션은 계획하지 않는다. 빈 테이블의 미사용 인덱스를 삭제하지 않는다. 테스트 쓰기는 격리된 로컬 Supabase에서만 수행한다. 롤백은 변경 커밋 되돌리기와 이전 Vercel 배포 복원으로 가능하다.
